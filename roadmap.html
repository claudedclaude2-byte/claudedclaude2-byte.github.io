01Built in private development

The evidence foundation

The core pieces already exist: records workflows, evidence search, provenance, claims, reviewed redaction and versioned dossiers.

  • Records requests, response history, expected-record comparisons and follow-up recommendations.
  • Document indexing, fingerprints, extraction outcomes, literal full-text search and structured filters.
  • Source snapshots, evidence-linked claims, conservative identity review and contradiction flags.
  • Preserved originals, reviewed text/PDF derivatives and revisioned dossiers with offline package verification.
What progress looks like

Bring these existing components together around a clear, dependable review journey.

02Next: planned, not started

A small offline evidence checker

Package a narrow part of the existing private pilot into a reproducible local checker.

  • Map the smallest source and dependency boundary, with provenance, licences and required notices.
  • Start with one fictional PDF-and-checklist example that produces source-page references and machine-readable expected results.
  • Provide a Windows Setup.exe installer with the required runtime, a Start menu shortcut and an uninstaller that preserves user records; verify offline first use.
  • Expand to three fictional packs and at least 12 documented checks for matches, missing or unreadable inputs and conflicts between declared values.
  • Record scoped Windows and Linux results, installation steps and limitations. Existing pilot checks do not certify a newly extracted package.
What progress looks like

A small reproducible package with documented outcomes and a clear licence and publication plan. The wider platform stays private; release is not yet agreed.

03Next

Make the first hour straightforward

Turn a developer-led setup into a clear first-use experience, then learn from a small number of guided evaluations.

  • Plain installation and startup guidance, folder preparation and a clear first-run walkthrough.
  • Useful recovery instructions when files, folders or inputs need attention.
  • Keyboard, text-size and accessibility improvements informed by observed use.
  • Guided fictional evaluations with investigators, researchers and document-workflow partners.
What progress looks like

A new operator can prepare, inspect, correct and review a fictional case with clear guidance.

04Planned direction

Give reviewers a richer workbench

Make it easier to see what changed, what is missing and what to ask for next. Priorities will follow evaluation findings.

  • Clearer comparison between revisions, with changed findings and their reasons beside the sources.
  • Bring request gaps and follow-up recommendations into the document review journey.
  • Link cited findings to source-change history and a more mature investigation Workspace.
  • Explore reviewed region-based redaction for scanned pages, with checks of the actual resulting pixels and text.
What progress looks like

Each addition solves an observed review problem while preserving source and revision traceability.

05Longer-term ambition

Connect people and existing workflows

Develop a path from an individual local workbench to useful partner integrations and shared review.

  • A clearer recipient verification kit and more portable review packages.
  • Evaluate connections with document-preparation, records-access and evidence-review tools.
  • Explore shared review, named roles, permissions and authentication for team use.
  • Assess an optional hosted workspace and controlled document intake as a separate product direction.
What progress looks like

A partner evaluation demonstrates a useful fit, with agreed data handling, access and responsibilities.

06Exploratory

Explore deeper discovery

Investigate ways to navigate larger evidence collections while keeping every useful result connected to its source.

  • Benchmark semantic retrieval alongside the existing literal and structured search.
  • Explore advisory assistance for finding related passages, conflicts and follow-up questions.
  • Evaluate additional document formats and jurisdiction-specific records workflows.
  • Measure retrieval quality and resource cost on a fixed fictional corpus before choosing an approach.
What progress looks like

Measured improvements in discovery, with inspectable citations and the reviewer retaining the decision.

    In progress: Path safety for workspace folders on Windows

    The safeguard for long workspace folder paths on Windows has been made on a development copy of the pilot: the pilot now says plainly, before any work starts, when a workspace folder is too long for the default Windows limit of 260 characters, and it cleans up only the leftover temporary folders that it can prove it created itself. A simulation of Linux on the development machine showed that 12 of the new tests failed when run as on Linux because of how those tests were set up, so the tests were corrected; the pilot itself was not changed. On the corrected version the full Windows checks completed on the development machine: the test suite ran with 8,302 tests passed, 471 skipped and 0 failed, and 563 of 563 deliberately introduced faults were caught by the tests. Its first-use run in an isolated, offline Windows sandbox on the development machine ran the full 80-step plan: 78 steps passed, 2 did not apply and none failed; it covered offline setup, the fictional matter journey, the refusals for workspace folders that are too long, a delivery from a folder within the limit, a run stopped part-way on purpose, and uninstalling. Its Linux test run in a container on the development machine ran 139 of 171 test files, with 6,305 tests passed, 370 skipped and 0 failed; the other 32 files test behaviour that exists only on Windows, and 90 of 90 deliberately introduced faults were caught on Linux. On the version before the correction, two sandbox attempts did not finish and one failed a leftover-folder check that the test kit had not expected; only the test kit was corrected. A run stopped part-way can still leave a temporary working folder behind; the install guide documents this and the safeguard does not remove it. These runs used fictional data only and ran on the same machine and Windows build as the development work, and the sandbox guest wrote its own receipts, so this is not a separate clean machine. The change has had no independent review, and none of this is acceptance or release.
