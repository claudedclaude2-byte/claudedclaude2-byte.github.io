01 / Records workflow

Request, response, gap, follow-up.

The platform grew from records-request tooling into a broader evidence workflow. It combines agency and incident discovery, request records, canonical request and appeal drafting, topic and jurisdiction routing, versioned legal-source data, deadline helpers, delivery and response history, and append-only request events. Jurisdiction coverage and legal-source currency must be assessed for the actual matter; this is not a promise of worldwide or automatic legal accuracy.

Close the loop around what is missing

Expected-record comparisons can distinguish supplied, partly supplied, denied, stated-not-to-exist and referenced-but-not-produced material when the available evidence supports that classification. Expected but unmentioned and unreceived records are labelled missing; insufficient evidence is labelled unclear. Neither establishes that a record does not exist.

Agency-history views, next-action recommendations and outcome feedback help organize a more informed follow-up. Outcome learning currently means historical agency aggregates such as response rates and elapsed time, with explicit sample sizes; it is not adaptive model training or demonstrated automatic request optimization. They work from stored history and defined rules; they do not guarantee a correct legal strategy or a successful response.

Sending is a separate authorized action

Drafting and next-action support do not authorize a live submission. Email, portal and other delivery paths have their own configuration and explicit human authorization requirements.

02 / Supplied evidence

Catalog once. Keep the extraction outcome.

Evidence indexing discovers supported folders and archive packages, catalogs files, calculates fingerprints and retains source-package relationships. Supported extraction and media probes add text or technical metadata, while failures and unavailable tools remain visible.

The evidence catalog connects cases, people, media and requests. Re-indexing is designed to be repeatable for a package location; moving a package can create a new source identity and should not be mistaken for global deduplication.

Search with an explicit match mode

SQLite full-text search supports token and phrase queries alongside structured and entity-aware filters. The search layer can compose source, claim, contradiction and publication-state context without replacing the underlying data. Some grouping and publication-state queries use a bounded 1,000-row prefetch; Workspace search exposes fewer filters than the command-line search layer.

Semantic search is future work

The current “hybrid” search combines existing full-text and structured intelligence. It does not provide embeddings, semantic/vector search, a vector database or an autonomous research agent.

03 / Source & meaning

Preserve what was relied on.

On-demand source snapshots record fetched bytes and a content fingerprint. Normalized text comparisons can distinguish meaningful changes from some presentation differences. Each capture remains a separate observation, including an unchanged result.

Claims retain explicit evidence anchors. A contradiction requires attributable claims rather than a free-floating assertion. People identities begin conservatively: candidate duplicates are suggestions, and merges or rejections require a reason and a recorded decision.

Signals for review, not verdicts

A differing date, changed source or conflicting value is useful to investigate. The platform does not automatically resolve credibility, prove identity, determine authenticity or rank the truth of a claim. A snapshot records what the tool captured; it is not independent source authentication.

04 / Reviewable outputs

Derive a package. Preserve the original.

The redaction workflow combines deterministic candidate detection and manual selections with individual human decisions. Text and supported PDF derivatives are written separately, verified to their defined scope and accompanied by review and audit information. The source is not overwritten. Detection is not complete PII discovery: names and addresses need manual selection. Current PDF redaction handles supported whole literal strings; it does not redact scanned pixels, images, audio or video.

Dossier generation produces versioned reports, manifests and citations to exact source passages. A recipient can verify a copied package with an independent offline verifier. A changed copied source can be rejected through its fingerprint mismatch.

Three questions remain separate

Is the package mechanically consistent? Does the cited material support the statement? Has a person actually reviewed and approved the material? A verifier answers only its defined first question.

05 / Two different local surfaces

The Workspace and the pilot.

Investigation Workspace

A loopback-only, read-only viewer composes requests, cases, search results, related intelligence and timeline information from an existing compatible SQLite database.

It remains a development slice. A clean checkout has no populated database or supported command to create a complete synthetic Workspace dataset. Authentication, multi-user operation and a general public API are not provided.

Bounded PDF pilot

A separate operator interface guides a small matter through folder checking, preparation, source-linked inspection, one correction round and a named review decision.

It is local and has no login. It is intended for a computer controlled by one operator, with evaluation inside the agreed private, supervised scope.

06 / The current evaluation route

A small matter with explicit limits.

DocumentsUp to 6 born-digital PDFs, 20 pages total, 10 pages per document. A matter can lower these limits. Reviewed scans share the same ceilings; files are read directly inside the selected folder, without recursive subfolder processing.

ChronologyRecognized ISO dates are collected; dates and time zones are not freely inferred.
OutputA portable local HTML review pack, draft working PDF bundle, factual brief, chronology, source index, discrepancy and missing-information reports, and preparation/engagement records, with source and bundle page links.
ApprovalRecorded reviewer identity, basis and attestation bound to the reviewed content. Changes make approval stale; withdrawal remains in history.
Unsupported or unread inputsListed explicitly. Word, email and spreadsheet files are not read by this pilot.

Scans need reviewed transcripts

Optional local OCR proposes text for scanned pages. A person compares it with the page image, corrects it and confirms each page's exact revision or rejects it. There is no bulk “confirm all.” Unconfirmed scanned pages remain unread for the pilot's citation flow.

OCR has local page limits and allowance accounting; those controls are not a subscription price or billing service. Names, dates, numbers, tables and handwriting require particular care.

A check does not promise usable content

Password-protected, corrupt or textless files can be listed as unread. A PDF extension or a folder file count does not prove that a document was readable. The review pack keeps those gaps explicit.

Python 3.12 or newer is the documented baseline. Windows is the current pilot validation focus. Results from a Linux container do not establish Windows or macOS operator acceptance, and a historical result does not accept a later candidate.

08 / Technical direction

Local data, explicit boundaries.

The platform uses Python, SQLite and FTS5, with server-rendered Flask/Jinja local interfaces and Waitress serving. The basic evidence workflow does not require a GPU, a standing vector service or mandatory cloud inference.

Local interfaces, offline package verification, on-demand external source fetches and optional delivery integrations have distinct network behaviors. “Local-first” describes the core data and workflow design; it does not mean every optional operation is offline.

Runtime records, databases, source captures, outputs and credentials belong outside the public presentation. The private implementation repository retains the development history and detailed contracts.
